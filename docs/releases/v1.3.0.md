# RD-API-Server v1.3.0

**Release date:** 2026-07-25

**Status:** Stable minor release

RD-API-Server v1.3.0 turns identity-provider group membership into console roles, and guarantees
one administrator account that no identity provider can take away. It is a backward-compatible
application upgrade over v1.2.0: the container still serves port `80`, persists
`/var/www/html/storage`, uses MariaDB/InnoDB, and preserves every RustDesk client route, JSON key,
and response shape.

> This release introduced a candidate channel and was published through it as `v1.3.0-rc.1` before
> promotion. The promoted image is built from the same source commit, `83308e4`.

> RD-API-Server is an independent, third-party, open-source project. It is not affiliated with,
> endorsed by, or sponsored by RustDesk or Purslane Ltd. RustDesk is referenced only to describe
> compatibility with the open-source client's public API.

## What changed

### Console roles from identity-provider groups

An operator declares "membership of this LDAP/FreeIPA or OIDC group grants this console role" under
**People & Access → SSO role mappings**. Membership is reconciled at every sign-in, through one
service invoked from all four login paths (console LDAP, client LDAP, console OIDC, client OIDC), so
a user's authority cannot depend on which client they last used.

Role assignments now carry provenance. Each is `manual` or `idp:<kind>:<provider>`, and a sign-in
reconciles only the grants its own provider owns. That is what lets revocation-on-departure and
hand-assigned roles coexist: a purely additive sync never revokes when someone leaves a group, and a
fully authoritative one destroys every hand-assigned role at the next login. Existing assignments
are backfilled as `manual`, so behaviour is unchanged until a mapping exists.

The exception is deliberately narrow:

- A mapping never writes `is_admin`, and an account holding it is skipped entirely.
- A `global` role grants every permission, including `settings.edit`, which can rewrite the SMTP
  configuration that delivers email sign-in codes. Targeting one requires
  `SSO_ROLE_MAPPING_ALLOW_GLOBAL=true`, an environment setting needing host access rather than a
  console session, re-checked at sign-in so disabling it revokes what it granted.
- Authoring a mapping is full-administrator-only, matching the existing rule for role mutation: an
  editor could otherwise point a mapping at a role more privileged than their own and sign in
  through the provider.
- Uncertainty never revokes. A failed directory or userinfo request, a provider with no configured
  claim, an Active Directory `memberOf;range=` truncation, an unreadable claim shape, and a group
  list too long to read in full all leave existing grants untouched. Only an explicitly empty group
  list revokes.

Group claims are read from the OIDC userinfo response only, via a per-provider claim name with dot
notation for nested claims. No ID token is parsed anywhere in this application, so reading groups
from one would trust an unverified assertion. **Entra ID and Google are therefore not supported** —
Entra emits groups only in the ID or access token, and Google has no groups claim. Keycloak,
Authentik, Authelia and Zitadel work; most require a mapper to be added before they emit anything.
**Active Directory nested groups are not expanded**; FreeIPA materialises indirect membership and
behaves as expected.

### A break-glass administrator

Every trust root in this application ultimately belongs to someone else. One account now carries
`is_protected_admin` and is outside all of it. The flag confers no permission — `is_admin` already
grants unconditional access — it only refuses the writes that would take that access away:
demotion, disabling, deletion, `force_sso`, and directory-driven demotion. A stored generated column
with a unique index makes "at most one" a database fact rather than an application convention.

It is never fillable and never reachable over HTTP. It moves only through
`php artisan rustdesk:admin:protect`, because an attacker holding an administrator session must not
be able to reassign the account that exists to survive a compromised console.

`php artisan rustdesk:admin:reset <username>` restores access from a shell when the console is
unreachable. It removes a security control only when explicitly told to and names what it removed:
`--unlink-federated-identities`, `--clear-force-sso`, and `--clear-2fa`. That last one is the only
path out of a lost second factor whose recovery codes are spent, which was previously unrecoverable
by any route. Both commands are audited, because CLI credential changes were otherwise invisible:
the console audit trail is written by HTTP middleware only.

### `ADMIN_PASS` is now optional

Leaving it unset no longer aborts a production boot. The first administrator receives a password
generated with `random_int()` over an alphabet that omits visually ambiguous characters, validated
against the same policy an operator-supplied value faces. It is shown once on stderr and written to
`storage/app/.initial-admin-password` as a root-owned `0400` file — so an application file-read
primitive cannot disclose it — and that file deletes itself when the account first signs in.

The seeder holds a row lock across the existence check and the insert, so two replicas booting
against one database cannot both generate a credential, and **an existing password is never rotated
on any subsequent boot**. Setting `ADMIN_PASS` keeps the previous behaviour and validation exactly.

### Release candidates

Tags suffixed `-alpha.N`, `-beta.N` or `-rc.N` now publish. They emit their exact version and move a
new `:next` alias, and deliberately do not move `:latest`, `:1` or `:1.2`. Promotion is a stable tag
on the same commit, so a candidate can never contain code that is not in the final release.

## Fixed

- **A directory could silently demote a local administrator on every sign-in.** With
  `LDAP_SYNC=true`, attribute synchronization wrote `is_admin` from directory group membership, and
  that membership test returns false whenever `LDAP_ADMIN_GROUP` is unset — which is its default. A
  linked administrator was demoted at their next login. The break-glass account is now exempt;
  ordinary administrators are still synchronized.
- The production runtime smoke read `docker logs` once immediately after readiness and could miss a
  line that had already been written, twice failing the release gate on a non-defect. It now polls.

## Upgrade

One migration adds `users.is_protected_admin` and designates the lowest-id administrator without a
federated identity. No configuration change is required.

```bash
docker compose pull rustdesk-api
docker compose up -d --force-recreate rustdesk-api
```

To test the candidate before it is promoted, pin the candidate rather than `:next`, which moves when
the next candidate is published:

```bash
RUSTDESK_API_IMAGE=ghcr.io/gigaionllc/rustdesk-api-server:1.3.0-rc.1 \
  docker compose up -d --force-recreate rustdesk-api
```

Confirm the designation after upgrading, and move it if it landed on the wrong account:

```bash
docker compose exec rustdesk-api php artisan rustdesk:admin:protect --show
```

## Rollback

No storage-layout change prevents rollback, but the migration adds a column. Rolling back to an
image that predates it is safe — the column is simply unused — while `php artisan migrate:rollback`
would remove the break-glass protection. Pin the previous release:

```bash
RUSTDESK_API_IMAGE='ghcr.io/gigaionllc/rustdesk-api-server:1.2.0@sha256:75d3b0e07af71c2c5e68be0b1bb86a5341cff298a50e297ed9e23995d25bd823' \
  docker compose up -d --force-recreate rustdesk-api
```

Rolling back restores directory-driven demotion of administrators and removes the SSO role mapping
screen; existing federated grants remain in the pivot but are no longer reconciled.

## Verification

- 641 PHPUnit tests with 3,453 assertions against isolated MariaDB/InnoDB.
- Pint across 300 files, PHPStan across 194 files.
- 71 Playwright tests with 21 intentional project skips.
- An adversarial review across six lenses over the SSO role mapping change before it was committed,
  every finding independently refuted before acceptance. Thirteen distinct defects were found and
  fixed, including two that would have shipped the feature broken.

## Known limitations

- **Not verified against a live FreeIPA or Authentik deployment.** The reconciliation rules are
  covered by tests with synthetic group lists and by an adversarial review, but no directory was
  available to exercise them end to end before release. The feature is inert until an operator
  creates a mapping, so an installation that does not use it is unaffected. If a mapping does not
  apply as expected, the SSO role mappings screen lists recent reconciliations and the reason each
  one did or did not change anything; please report what that panel shows.
- Entra ID and Google cannot supply group claims, as described above.
- Active Directory nested groups and primary-group membership are not expanded.
- Hosts-file publication of an identity provider is IPv4-only.
