# RD-API-Server v1.4.3

**Release date:** 2026-08-16

**Status:** Patch release. The browser remote desktop shipped in 1.4.0 never actually ran; this is
the release where it does. No breaking changes.

---

## What was wrong

Opening the viewer produced its manual connection form — three empty boxes asking for an ID server,
a peer ID and a base64 server key — on a page where the server had injected all three, correctly,
two lines above.

The published copy of the viewer flattened `src/*` to the document root while leaving `vendor/`
beside it. The modules import the vendored trees relative to the source layout:

```js
import nacl from '../../vendor/tweetnacl/nacl.js';       // from src/crypto/
import { decompress } from '../../vendor/fzstd/index.js'; // from src/render/
import { decompress } from '../vendor/fzstd/index.js';    // from src/
```

Those are correct only while `src` and `vendor` are siblings. Flattened, every one of them resolved
a directory too high — `/assets/vendor/...`, where the console's own Bootstrap and jQuery live and
no such file exists. The browser 404ed on the first, and a failed import takes the **entire module
graph** with it. Nothing ran: not the configuration handling, not the connect logic, not the
viewer's own setup. The page was the bare HTML document, which is why it offered a form.

There is no build step in this client — `src/` and `vendor/` *are* the artifact — so nothing
rewrote those paths. The published layout simply had to match the source, and did not.

## The fix

The publisher and the image build now preserve the source layout, so `/assets/webclient/src/…` and
`/assets/webclient/vendor/…` sit exactly as they do in the repository. The viewer is served from
`/assets/webclient/src/ui/viewer.html`.

The publisher also clears its whole target directory first. Removing only the directories it is
about to write left the previous layout's files behind at paths nothing serves — copies that drift
silently and make it impossible to tell by looking which one the application reads.

## Why no test caught it

Every existing test loaded the viewer from `web-client/`, where the layout is correct by
construction. The published copy is a different shape, and nothing had ever loaded it.

Two tests now close that seam:

- Every import in the published tree is resolved the way a browser resolves it, including bare
  specifiers, which this client cannot use because it ships no import map.
- The published copy is asserted byte-identical to the source, without needing Node, so a PHP-only
  run still catches an edit made to one copy and not the other.

The browser suite gains coverage for free: `tools/serve.mjs` serves the package root, which is now
the same shape as the published tree, so the fifteen Chromium tests exercise the layout that ships.

## Also fixed

The feature test suite deleted the published viewer on every run. Its stub tested a path that had
moved, so it always believed the assets were missing, and its teardown removed the whole published
tree rather than the two files it had created.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration and no configuration change. A source deployment must republish:

```bash
node web-client/scripts/install-assets.mjs
```

---

## Verification

- **661 PHP tests**, including the two new published-layout tests.
- 253 web-client unit tests and 15 browser tests in real Chromium.
- The image build was inspected directly: every relative import in the published tree resolves to a
  file that exists, and the viewer is at the path the application reads.

**Still not verified end to end:** a full session against a live peer through this published copy.
The module graph now loads and the configuration reaches the viewer; whether the WebSocket path
through a given reverse proxy works is what the diagnostics page's browser probe is for.
