# RD-API-Server v1.6.0

**Release date:** 2026-08-17

**Status:** Minor release. Two additions for troubleshooting; no breaking changes, no migration, no
configuration change.

## The version is on screen

It now appears in the sidebar footer on every page. It is the first question on every support
thread, and an operator should be able to answer it from wherever they already are rather than
hunting for a settings screen.

## A support report worth attaching to an issue

**System → Support report** produces the thing a maintainer otherwise has to extract one question
at a time:

| | |
|---|---|
| Environment | Version, Laravel, PHP, OS, web server, environment, debug mode |
| Configuration | What is set and what is not — never the values |
| Browser remote desktop | The full diagnostics report, inline |
| Database | Driver, version, migrations applied, device and user counts |
| Recent log | The last 400 lines |

### What is removed before it leaves the machine

Everything in the report passes through a redactor first:

- IPv4 and IPv6 addresses, and MAC addresses
- Hostnames, whole URLs including their paths
- Email addresses
- Base64 key material
- RustDesk peer ids
- Any value whose *name* suggests a secret — `DB_PASSWORD`, `ADMIN_PASS`, `"api_key"`,
  `Authorization: Bearer …`. Matching the name is what catches a password of `hunter2`, which has
  no pattern to recognise.

**The same value always becomes the same placeholder.** `<host-1>` twice means the same host twice;
`[redacted]` twice means nothing. A report nobody can reason from is one nobody will ask for.

Values that are secret by name are never read in order to be hidden. The report says whether a
server key is configured and which half of the pair it is — never what it contains.

### What deliberately stays

Versions, error messages, file names, stack frames, log levels, `127.0.0.1`, timestamps, and
counts. A report stripped of everything is just a button nobody presses.

### It is shown before it is sent

The page displays the finished text and says plainly that redaction is a large reduction in what
escapes rather than a guarantee. The last check on "is this safe to publish" has to be a person who
knows their own deployment.

The report requires the `settings.view` permission: it describes the deployment, which is not for
every account with a console login.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

Nothing else.

## Verification

- **692 PHP tests**, including ten on the redactor alone.
- 253 web-client unit tests and 15 browser tests.

Two defects were found by generating a real report against a running deployment and reading it,
after the unit tests were already green — both are now pinned:

- A harmless `production.DEBUG:` pair consumed the whole of a following `DB_PASSWORD=hunter2`,
  so the password was never examined and shipped in the report.
- A kernel release (`6.6.87.2-microsoft-standard`) is a valid IPv4 address and was being replaced,
  removing the one piece of platform information that line existed to carry.
