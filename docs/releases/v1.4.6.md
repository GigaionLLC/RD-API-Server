# RD-API-Server v1.4.6

**Release date:** 2026-08-17

**Status:** Patch release. Documentation and shipped examples only — no application behaviour
changes. No configuration change is required.

---

## The examples now say which key belongs where

1.4.5 made it impossible for this server to hand out a private key. This release fixes the reason
one was configured in the first place.

The shipped Compose files and `.env.example` are what an operator copies, and they were the last
place still naming `RUSTDESK_KEY` with no indication of which half of the pair it wants. Worse,
`.env.example` documented device enrollment and WebSocket options while omitting the ID server,
relay, API server and key **entirely** — so someone working from it had nothing at all to check
their guess against, and the two candidate files sit side by side with near-identical names.

They now name `RUSTDESK_PUBLIC_KEY`, state that `id_ed25519.pub` is wanted and `id_ed25519` is not,
and say what happens if you get it wrong: the value is handed to every client, and anyone holding
the private half can impersonate your ID server.

**No existing deployment needs to change anything.** The Compose files read `RUSTDESK_PUBLIC_KEY`
and fall back to `RUSTDESK_KEY`, so an existing `.env` keeps working untouched. All four
combinations were verified with `docker compose config`.

## The examples can configure the remote desktop at all

The shipped Compose files passed none of the four WebSocket settings through, so the browser remote
desktop could not be configured from them — an operator had to know to add the variables. All four
are now present and empty.

The full-stack example goes further and wires the container-carried transport:

```yaml
- RUSTDESK_WS_ID_UPSTREAM=hbbs:21118
- RUSTDESK_WS_RELAY_UPSTREAM=hbbr:21119
```

Everything in that file already shares a network, so the service names resolve and the remote
desktop works on the console's own hostname with no second certificate and no reverse-proxy change.
The 21118 and 21119 publications are commented out, since nothing outside the stack needs them any
more, with a note explaining when you would want them back.

The trade-off is stated where the setting is: relayed session video then passes through the API
container. Clearing those two and setting `RUSTDESK_WS_ID_URL` / `RUSTDESK_WS_RELAY_URL` keeps it
out of the media path.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

Nothing else. If you copied an earlier example, the only worthwhile edit is confirming that your
key is the 32-byte `id_ed25519.pub` and not the 64-byte `id_ed25519` — **System → Remote
diagnostics** tells you which you have.
