# RD-API-Server v1.4.0

**Release date:** unreleased — draft

**Status:** Minor release. Adds a browser remote desktop; no breaking changes.

RD-API-Server v1.4.0 adds a **remote desktop that runs in the browser**. From the device list,
**Connect** opens a session against that peer — screen, sound, mouse, keyboard, clipboard and chat —
with no plugin, no download and no client install.

It is a backward-compatible application upgrade over v1.3.0: the container still serves port `80`,
persists `/var/www/html/storage`, uses MariaDB/InnoDB, and preserves every RustDesk client route,
JSON key and response shape. Nothing about the existing client API changes.

> RD-API-Server is an independent, third-party, open-source project. It is not affiliated with,
> endorsed by, or sponsored by RustDesk or Purslane Ltd. RustDesk is referenced only to describe
> compatibility with the open-source client's public API.

## The browser remote desktop

### What it does

| | |
|---|---|
| Video | VP8, VP9, AV1, H.264, H.265 — negotiated with the peer, decoded with WebCodecs |
| Monitors | Enumerated from the peer; switch between them mid-session |
| Cursor | Remote pointer drawn on its own layer, with the peer's shape |
| Audio | Opus, muted by default |
| Input | Mouse, keyboard, wheel, drag. Ctrl+W and Escape reach the remote machine in fullscreen |
| Clipboard | Text and HTML, both directions |
| Chat | Message whoever is at the remote machine |
| Quality | Presets plus an explicit frame-rate ceiling |

**Not implemented yet:** file transfer and terminal.

**Not possible from a browser**, and unlikely to change: direct peer-to-peer. Browsers cannot
hole-punch, so **every session is relayed through `hbbr`**. Budget relay bandwidth before offering
this widely.

### How it works

The page speaks the RustDesk protocol **directly to `hbbs` and `hbbr` over WebSocket**. This server
hands the browser its connection details and then steps out of the way — it is never in the media
path, proxies nothing, and runs no additional process. `hbbs` binds port 21118 and `hbbr` binds
21119 for WebSocket in every stock build since server 1.1.6, so no server-side change is required.

The viewer is a standalone package under `web-client/`: plain ES modules, **no build step**, no
bundler, and no code generation. The whole session — socket, decryption, protocol decoding, video
decode and compositing — runs in a Worker, so the interface stays responsive while the stream does
not.

### Requirements

- **Chrome or Chromium, on desktop.** Firefox and Safari are not supported.
- **A secure context.** WebCodecs is unavailable otherwise, and an HTTPS page cannot open a plain
  `ws://` socket.
- rustdesk-server **1.1.6 or newer** (1.1.15+ recommended).

### Setting it up

```bash
node web-client/scripts/install-assets.mjs
```

Then, unless the console is served from `http://localhost`, point the viewer at a TLS terminator in
front of the WebSocket ports:

```env
RUSTDESK_WS_ID_URL=wss://rustdesk.example.com/ws/id
RUSTDESK_WS_RELAY_URL=wss://rustdesk.example.com/ws/relay
```

**[docs/web-client-deployment.md](../web-client-deployment.md)** has nginx and Caddy configuration
and two traps that are worth reading before deploying:

- **Do not forward `X-Real-IP` or `X-Forwarded-For` to port 21118.** `hbbs` overwrites the
  connection address with those headers and keys its pending-response map on the result, so every
  session behind one public IP collapses together and concurrent operators take each other's
  connections. Two people behind one NAT is enough to trigger it.
- **Never TCP-proxy port 21115 or 21117 from localhost.** Both servers treat a non-WebSocket
  loopback connection as an unauthenticated admin console. Terminating `wss` in front of 21118 and
  21119 is safe; a plain TCP proxy in front of the other ports is not.

### Security

Authorization is enforced **server-side and per device**. Both viewer routes re-check the operator's
device scope, so the device list is a boundary rather than a suggestion.

**The peer's connection password is never held or transmitted by this server.** The operator types
it into the viewer, and it is used only to derive the proof the peer expects. Session traffic is
end-to-end encrypted between browser and peer; the relay carries ciphertext it cannot read.

Note that stock `hbbr` relays for anyone presenting a matching session UUID unless a relay key is
configured. Setting one is worthwhile defence in depth.

## Upgrading

No configuration change is required, and no database migration is involved. The existing client API
is untouched.

To use the remote desktop, run `install-assets.mjs` and set the two `RUSTDESK_WS_*_URL` values. The
device page states plainly when either step has been missed rather than showing a blank screen.

## Verification

- **173 protocol and unit tests** covering the wire codec, cryptography, session state, input
  encoding, clipboard and chat.
- **10 browser tests** in real Chromium covering WebCodecs, canvas compositing, the audio graph and
  the Worker — including encoding a frame with a real encoder, decoding it through the client, and
  asserting the pixels arrive.
- Verified end to end against a live peer: rendezvous, relay, the cryptographic handshake, login,
  video, multi-monitor switching, cursor caching, audio, input, and clipboard round-trip.

## Known limitations

| | |
|---|---|
| File transfer, terminal | Not implemented |
| Firefox, Safari, mobile | Not supported |
| Direct peer-to-peer | Not possible from a browser; all sessions are relayed |
| Reconnect | A dropped session must be reconnected manually |
