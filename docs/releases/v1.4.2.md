# RD-API-Server v1.4.2

**Release date:** 2026-08-16

**Status:** Patch release. Adds a Remote control screen, removes every path that could connect
without being asked to, and fixes a viewer that rendered as a thumbnail. No breaking changes.

---

## Nothing connects on its own

A remote desktop session is visible on the other machine and interrupts whoever is sitting at it.
Starting one has to be a decision someone made — not a side effect of opening a page, restoring a
browser tab, or mis-clicking a row in a list.

**Connect** on a device therefore no longer opens a session. It opens the **Remote control** screen
with that ID filled in, and waits.

The viewer's auto-connect handling has been **removed outright rather than defaulted off**, so no
configuration value and no URL parameter can bring it back. A browser test loads the viewer with
both former switches set and asserts that no socket is opened at all.

---

## Remote control

A screen that takes a RustDesk ID directly, at **Control → Remote control**.

- The ID field is pre-filled when arriving from the device list, and free to type into otherwise.
- Known devices can be picked from a list, which fills the field rather than navigating — the
  operator still presses Load, and then Connect.
- Server details are filled in from this deployment's own configuration. An operator never types an
  ID server, a key, or an endpoint.
- The password is never in the form or the URL. It belongs to the peer, this server does not hold
  it, and a secret in a URL lands in browser history and every access log on the way.

**An ID that is not in the device list is accepted** — from an operator whose device permission is
unrestricted. This is what a support desk needs when an ID arrives over the phone for a machine
that has never checked in here. An operator scoped to a group keeps that boundary: for them the ID
field reaches only their own devices, because otherwise typing an ID by hand would be a way around
the scope.

## Fixed

### The viewer rendered as a thumbnail

The remote desktop appeared as a 300×150 box with its toolbar wrapped into a column and its canvas
clipped away. Its stylesheet was pushed to a Blade stack the layout does not render, so every rule
was discarded silently and the iframe fell back to its intrinsic size. The diagnostics page had the
same defect.

### The viewer could ask for details it had been given

Configuration is injected into the viewer document by replacing a marker. When that replacement
found nothing, it did so silently, and the viewer fell back to its manual connection form — asking
the operator for an ID server and a base64 key, which reads as a half-finished feature rather than
a failure. The injection is now verified, and a document that cannot carry configuration raises an
error naming the cause.

### Compiled views could survive an image upgrade

`storage/` is a persistent volume, so Blade views compiled by a previous image are still there
after `docker compose pull`. `view:cache` does not remove what it finds, and Blade only recompiles
when the source is newer — a comparison that Docker's preserved build timestamps can lose. Views
are now cleared before they are rebuilt, so the rendered console always matches the image.

---

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration and no configuration change. The `/admin/devices/{id}/connect` URL still works and now
redirects to the Remote control screen.

## Verification

- **657 PHP tests**, including that Connect redirects rather than connecting, that no configuration
  key which would auto-connect reaches the viewer, that a pasted ID keeps its digits but not its
  punctuation, that a hostile ID cannot escape the injected configuration, and that a scoped
  operator cannot reach outside their scope by typing an ID.
- **15 browser tests** in real Chromium, including one that loads the viewer with both former
  auto-connect switches set and asserts no WebSocket is opened.
- 253 web-client unit tests.

**Not verified:** the proxied WebSocket transport from 1.4.1 against a live `hbbs` behind a second
reverse proxy. The diagnostics page's browser probe is the way to check that in place.
