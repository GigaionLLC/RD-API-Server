# RD-API-Server v1.4.1

**Release date:** 2026-08-16

**Status:** Patch release. Makes the browser remote desktop deployable without a reverse-proxy
change, and adds a page that says why it is not working. No breaking changes.

v1.4.0 shipped a remote desktop that runs in the browser. Standing it up, though, meant a second
TLS terminator, a second certificate, two more public ports and a hand-written WebSocket vhost —
and one wrong header in that vhost silently breaks concurrent sessions. That is a great deal of
apparatus for a feature whose whole appeal is that there is nothing to install.

This release removes it for the common case.

> endorsed by, or sponsored by RustDesk or Purslane Ltd. RustDesk is referenced only to describe
> compatibility with the open-source client's public API.

## Two lines instead of a vhost

```yaml
- RUSTDESK_WS_ID_UPSTREAM=hbbs:21118
- RUSTDESK_WS_RELAY_UPSTREAM=hbbr:21119
```

`host:port` as reachable **from this container** — on a Compose network, the service names. The
runtime then serves `/ws/id` and `/ws/relay` on the console's own hostname and certificate and
forwards them to `hbbs` and `hbbr`, which speak plain `ws` only.

Nothing else needs configuring. The viewer derives its endpoints from `APP_URL`, so there is no
second place to keep in step and no `RUSTDESK_WS_*_URL` to set.

| | Before | Now |
|---|---|---|
| Certificates | A second one for the WebSocket host | The console's own |
| Public ports | 21118 and 21119, behind TLS | None beyond the console |
| Reverse proxy | A hand-written vhost with two location blocks | Unchanged |
| Header hygiene | Yours to get right | Handled in the container |

### What it costs

**This container joins the media path.** Relayed session video passes through it, which is exactly
what the direct arrangement avoids. For a handful of concurrent sessions that is not measurable;
for many, keep the direct arrangement — explicit `RUSTDESK_WS_ID_URL` and `RUSTDESK_WS_RELAY_URL`
still win, so moving between the two is a configuration change rather than a redeployment.

### What it prevents

`hbbs` overwrites a connection's address with `X-Real-IP` — falling back to `X-Forwarded-For`,
unvalidated — and then keys its pending-response map on the result. A proxy that forwards those
headers, which most do by default, makes every operator arriving through it collapse onto one key
and take each other's `PunchHoleResponse`. Two people behind one public IP is enough.

The runtime blanks those headers toward `hbbs`. Doing it here means an operator cannot get it
wrong by hand.

### Three details worth knowing

- Nginx resolves a literal hostname in `proxy_pass` **once, at startup**, and refuses to start when
  it does not resolve. Written that way this container would fail to boot whenever `hbbs` happened
  to be slower to start, then hold that first address for the life of the process and proxy a
  restarted `hbbs` into a black hole. Resolution goes through a variable and the container's own
  resolver instead.
- Upstream values are interpolated into a configuration file, so they are validated to `host:port`
  and nothing else. Anything else is refused at start-up.
- Both must be set. Half a configuration produces a rendezvous endpoint with no matching relay — a
  session that connects and then stops, which is harder to diagnose than one that never starts.

## A page that says what is wrong

**System → Remote desktop** reports every condition that would otherwise present as "cannot
connect" against a server that is running perfectly well:

| Check | Catches |
|---|---|
| Viewer assets | Published copy missing from the document root |
| ID server | `RUSTDESK_ID_SERVER` unset |
| Server key | Sessions that cannot be verified end to end |
| Secure context | An `APP_URL` where WebCodecs is unavailable, so no video can be decoded |
| Reverse proxy | A forwarded HTTPS header the application does not trust, usually a missing `TRUSTED_PROXIES` |
| Transport | Which arrangement is configured, or none |
| Upstreams | A name that does not resolve, a container on another network, a closed port |

It also opens a real WebSocket to the endpoint **from the operator's browser**. That is the check
that matters — the browser, not this container, is what has to get through the reverse proxy — and
it is the only one this server cannot make on their behalf.

### Why the transport is not editable here

The WebSocket route is part of the container's own web-server configuration, rendered once at
start-up. A value editable in the console could not change that configuration without a restart,
and in the meantime the two would disagree — the console claiming one thing while the server did
another. The page states this rather than leaving the absence of a form unexplained.

## Also fixed

- An HTTPS console with no WebSocket endpoints configured rendered a viewer that looked ready and
  then failed to connect, which reads as an unreachable server rather than a missing setting. The
  device page now names the values that are missing.
- Server-side tests for the viewer routes, which 1.4.0 shipped without: both routes re-run the
  operator's device scope, the iframe document is gated exactly like the page that embeds it, and
  no peer password appears in the injected configuration.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration, no configuration change, and the existing client API is untouched. A deployment
already using explicit `RUSTDESK_WS_*_URL` values keeps working exactly as it did.

To adopt the new arrangement, add the two upstreams and remove the WebSocket vhost. The 21118 and
21119 port publications can go too, since only this container needs to reach them.

## Verification

- **657 PHP tests**, including sixteen new ones covering the viewer routes' authorization, the
  endpoint derivation for both transports, and the diagnostics page.
- 253 web-client unit tests and 14 browser tests, unchanged from 1.4.0.
- The rendered Nginx configuration was verified inside the built image in all three states —
  enabled, disabled, and refused on a half or malformed configuration — including that the
  container starts when the upstream does not resolve.

**Not verified:** the proxied transport has been exercised through the rendered configuration and
its validation, not yet against a live `hbbs` behind a second reverse proxy. The most likely
remaining obstacle is an outer proxy that does not forward the `Upgrade` and `Connection` headers;
the browser probe on the diagnostics page reports exactly that case.
