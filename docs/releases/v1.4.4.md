## The remote desktop runs

Three separate faults produced one symptom — a viewer that showed a manual connection form asking
for an ID server, a peer ID and a base64 key, on a page where the server had injected all three
correctly. 1.4.2 fixed the first, 1.4.3 the second, and this release the third and last.

**The document could not load its own scripts.** The viewer's HTML is served from an application
route, not from the directory the file lives in, and relative URLs resolve against the document's
address. `src="./viewer.js"` on `/admin/remote/frame` therefore asked for
`/admin/remote/viewer.js`, which does not exist. One 404 stops the whole module graph — nothing
runs, and what renders is the bare HTML document. The served document now carries a `<base>`
pointing at the published assets.

The trailing slash on that base is load-bearing, and Laravel's `asset()` strips it. Without one the
last path segment is treated as a filename and every relative URL still resolves a directory too
high — the same 404, from a `<base>` that looks correct. That variant was caught only because the
fix was checked in a browser rather than assumed.

## A check for the wrong half of the key pair

An Ed25519 signing key is 64 bytes — a seed followed by the 32-byte public key — and RustDesk
writes both halves to disk with confusingly similar names. `RUSTDESK_KEY` wants the **public** one.

Configuring the private half is not a typo with a cosmetic result. This value is handed to every
client and to the viewer, so the key whose entire purpose is to prove the server's identity gets
published to anyone who asks for a client configuration. Anyone holding it can impersonate the ID
server to every client on the deployment. It also does not work: `hbbs` compares the presented key
against its own and refuses the connection, reporting a licence mismatch.

The diagnostics page now recognises a 64-byte value, says plainly what it is, prints the correct
32-byte public key extracted from it, and says to rotate the pair — because a private key that has
been distributed is no longer private. A value that is neither 32 nor 64 bytes of base64 is
reported too.

This was found by configuring a test deployment from a real one and watching `hbbs` refuse it.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration and no configuration change. Then open **System → Remote diagnostics** and press
**Test from this browser**: it is the one check this server cannot make on an operator's behalf,
since the browser rather than the container is what has to get through the reverse proxy.
