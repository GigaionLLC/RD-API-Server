# RD-API-Server v1.4.5

**Release date:** 2026-08-16

**Status:** Patch release with a security improvement. No breaking changes; no configuration change
is required.

---

## The server can no longer hand out a private key

This application never signs anything. It holds the RustDesk server key for exactly one purpose:
giving it to clients and to the browser viewer, which use it to **verify** that the server signing a
handshake is the one they were configured for. Verification needs the public half and nothing else,
so the private half has no use here — a search of the codebase finds no signing call at all, and the
key is read in exactly two places, both of which hand it out.

It was nonetheless possible to configure. An Ed25519 signing key is 64 bytes — a random seed
followed by a copy of the 32-byte public key — and RustDesk writes the halves side by side:

| | |
|---|---|
| `id_ed25519.pub` | 32 bytes. Belongs in `RUSTDESK_PUBLIC_KEY`; goes to clients |
| `id_ed25519` | 64 bytes. Stays on the server; never distributed |

Point the configuration at the second and this server published, to every client that requested a
configuration, the key whose entire purpose is to prove the server's identity. Anyone holding it
can impersonate the ID server to every client on the deployment.

### What changed

Both distribution paths — the client-config generator and the browser viewer — now go through one
service that yields only the public half, **deriving it when a private key is supplied**.

Deriving rather than refusing is deliberate. An operator who made this mistake gets a working
deployment and a loud diagnostic instead of a broken one and a puzzle, and `hbbs` refuses a client
presenting a private key anyway, so passing it through helped nobody. The diagnostics page still
reports the misconfiguration in full, prints the correct public key, and says to rotate.

A value that is neither half of a pair is dropped rather than distributed. Handing out a malformed
key breaks every client with an error none of them can diagnose; handing out nothing leaves the
deployment merely unauthenticated, which the diagnostics page also reports.

> **If your configuration holds the private key, rotate the pair.** It has been distributed to
> every client that fetched a configuration, and correcting the setting does not un-distribute it.

## `RUSTDESK_PUBLIC_KEY`

A clearer name for the same setting, because the two files have near-identical names and the wrong
one is easy to grab:

```env
RUSTDESK_PUBLIC_KEY=<contents of id_ed25519.pub>
RUSTDESK_PUBLIC_KEY_FILE=/path/to/id_ed25519.pub
```

**`RUSTDESK_KEY` and `RUSTDESK_KEY_FILE` keep working indefinitely.** They are the conventional
spelling across the RustDesk ecosystem, and breaking them would fail *silently*: an unset key
disables peer verification rather than raising anything, so an upgrade would quietly downgrade
security. The explicit name wins when both are set.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

No migration, no configuration change. Renaming the variable is optional.

## Verification

- **668 PHP tests**, including six covering the key service directly: that a private key never
  leaves as one however it is configured, that a key file pointed at `id_ed25519` is handled the
  same way, that a malformed value is dropped rather than distributed, and that the conventional
  environment name still resolves.
